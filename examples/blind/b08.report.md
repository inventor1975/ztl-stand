## APPROXIMATED
- No atan/tan in the format. HFOV = 2*atan(w/2f) then W = 2*D*tan(HFOV/2) collapses algebraically, tan(atan x) = x, to W = D*w/f. I used the exact identity as the law and said so in `source`. The answer is neither safer nor riskier. It is exact, but it drops the HFOV step as a named quantity (HFOV is never reported).
- "At the shortest / longest distance": the format has no way to say "evaluate at D = D_min". I stated the requirement for all D in the range. W is increasing in D and s is increasing in D, so "for all D" is equivalent to the binding end the problem names. Same result here. It would NOT be equivalent for a requirement non-monotone in D, or for two requirements needing different D ends of the same quantity.
- "IC >= sensor diagonal" needs a derived quantity (requirements must name a derived one), so I added ICd == LENS.IC. The diagonal 17.5 is a bare number in the requirement, not a given with a unit. The problem's own 17.5 mm is rounded (sqrt(14.13^2 + 10.35^2) = 17.52 mm); I used 17.5 as stated, which is the problem's choice and is slightly riskier than 17.52 (L1/L3/L4/L5 have 17.6, so it does not change the answer).
- f "5.0 mm +-3%": tolerance is relative, used as given.

## COULD NOT EXPRESS
- Trig functions (atan, tan), so HFOV and any requirement on field of view cannot be stated or reported. Only the identity-reduced forms work.
- A requirement evaluated at a chosen point of a given range (e.g. "at the shortest D"). Only "for all" exists.
- A requirement that compares a catalog field to a constant without a derived copy (IC >= 17.5 needed a dummy law).
- The sensor diagonal as a computed value from 4096 x 3000 x p (pixel counts are not used at all; w and diagonal given as stated).
