# b10 report (problem 10, API capacity plan, two modes)
Files: b10.json (the brick that runs), b10_modes_crashes.json (first, natural encoding with `modes`; crashes the tool).

## EXPRESSED FAITHFULLY
- 4 instance types (mu, tolerance +-10/10/12/12%, price) as a listed catalog; N = integers 2..12 as a second slot, so all instances are one type.
- lambda = 1800 +-10%; gateway 5..12 ms and database 15..30 ms as ranges; M/M/1 utilization and T99 = ln(100)/(mu - lambda/N_active) as laws.
- Requirements: normal TN <= 150 ms and rhoN <= 0.75; degraded TD <= 300 ms. Objective minimize price*N. Same lambda/gw/db in both situations.

## APPROXIMATED
1. ln(100) irrational: given range [4.605170, 4.605171]. Tiny, safe (bracket).
2. lambda written as range [1620, 1980.001], not 1800 +-10%. Reason: the stand solves at the nominal (range midpoint), and a nominal exactly on the pole mu = lambda/N_active (I3 N=2, I2 N=4, I2 N=5 degraded) crashed it. Upper end widened by 0.001 req/s: safer (by 5e-5 %).
3. "rho < 1" in degraded mode written as rhoD <= 1 (no strict op). Safe in effect: rho = 1 gives infinite T99 anyway.
4. Two modes written as ONE brick with two copies of the laws (N and N-1 baked in: TN, TD, rhoN, rhoD) instead of `modes`. Equivalent for these one-sided "for all" bounds; the `modes` version crashes (below).
5. Stability (mu > lambda_i) cannot be stated as a domain condition of the T99 law; it is only enforced through the rho requirements. Without rhoD, an unstable design passed (see TOOL OUTPUT note).

## COULD NOT EXPRESS
- A domain condition on a law ("valid only if rho < 1", strict inequality). No strict `<` op.
- A mode with its own law/N (here done by duplicating quantities). The `modes` feature with a division law crashes when some design is undecided in a mode (see below).
- The cost unit "per instance-hour" (price unit is plain USD; objective is price*N, dimensionally USD).

## TOOL OUTPUT
- Natural encoding (`modes`, one derived Tend, `dn` given overridden per mode): Python traceback, not a BRICK ERROR: CheckError "definitions depend on each other in a cycle or on an unknown" (checker.py solve_at). Isolated: happens for I2 N=4 and N=5 (denominator mu - lambda_i spans 0 over the tolerance box, so a mode is undecided); the same two designs in a plain brick are reported "undecided". Also crashes (same message) in plain bricks if a division's NOMINAL denominator is exactly 0. Neither is a cycle; misleading message.
- Without any rho requirement the stand returned EARNED for I1 N=2 ($0.34): lambda_i = 900 > mu = 220, T99 negative (-6.8 ms), so Tend = 11..36 ms "passes". The format does not guard this.
- Final (b10.json): verdict EARNED, design I2 (mu 450 +-10%, $0.34) x N=7, objective 2.38 USD/h. optimal: false ("1 cheaper design undecided: optimal only among the decided ones"). designs_tried 19 (of 44 combinations; 15 failed at nominal, 4 judged, 1 undecided).
- Guaranteed: TN 37.47..79.70 ms, rhoN 0.4675..0.6984, rhoD 0.5455..0.8148, TD 40.47..103.40 ms. All "ZTL, outer range" (interval reading, sound, possibly wider than the truth).

## DOES THE ANSWER LOOK RIGHT
Yes, checked by hand for I2 N=7: rhoN max = 1980.001/(7*405) = 0.698413 (matches 1980001/2835000). TN max = 12 + 30 + 1000*4.60517/(405 - 1980.001/7) = 42 + 4605.17/122.143 = 42 + 37.70 = 79.70 ms (tool 79.7032). Independent worst-case enumeration of all 44 (type,N) pairs (monotone worst case at lambda max, mu min): cheapest feasible is I2 N=7 at 2.38 (next: I2 N=8 and I3 N=4 at 2.72). So the true optimum equals the tool's; the "optimal: false" is overcautious: the undecided cheaper design is I2 N=4 or 5 (pole in the box), which truly fails rhoN <= 0.75 (1980/(4*405) = 1.22). Feasible set also: all I3 N>=4, I4 N>=3, I2 N>=7; I1 none (the tool's REFUTED for every I1 N agrees).

## DOC GAPS
- BRICKS.md says nothing on division by an expression that can be zero/negative (pole at nominal crashes; pole in the box = undecided; negative denominator silently accepted).
- `modes` section does not say what happens when a design is undecided in a mode (it crashes here).
- "nominal" is the range midpoint / value; this matters (poles) but is not stated.
- Dimension note: dividing a quantity of unit "1/s" by "1/s" ok; ln(100) must be a bracketed given (no transcendental functions): not stated.
