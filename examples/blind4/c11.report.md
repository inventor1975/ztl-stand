# c11 report: Steam sterilisation program, one universal program for four loads (problem 11)

Submitted brick: `c11.json` (generated by `work_c11/gen.py 8 2 60 c11.json B`). It is the OPTIMISTIC relaxation of the
problem (see APPROXIMATED), so its verdict REFUTED is meant to carry over to the real problem. Verdict: **REFUTED**
(all 31860 designs fail; 5 min 47 s). A conservative twin (mode A) was used only to test the EARNED side.

## EXPRESSED FAITHFULLY
- T_set in {121,124,126,130,134} with drying time (25/23/22/20/18 min) as a listed catalog.
- Per-load packaging from its own allowed list (four slots, four catalogs; tau multiplier, max chamber temp, price as fields).
- T_ch = T_set + dT, dT in [-0.5, 1.5] (a given range, `define Tch`); T0 in [45, 80]; both independent, "for all".
- tau = base tau x multiplier (`define`), units s; spore D121 = 1.5 min, z = 10 C, reference 121.1 C as givens with units.
- Cold-spot law and the 10^((Tcs-121.1)/10) kill rate with real `pow`, `exp`.
- R2 Dm = t_h * 10^((T_set+1.5-121)/25) <= budget; R3 T_set+1.5 <= packaging max (as a margin >= 0); R4 weekly time
  = sum cycles x (15 + t_h + drying) <= 48 h (derived in h); cost objective 0.90 EUR/min x cycle minutes + pack prices
  x packs x cycles (an exact expression of catalog fields; the stand finds the cheapest).
- Per-load R1, R2, R3 as separate requirements (13 requirements in c11.json).

## APPROXIMATED
1. **The integral for LR.** The format has no integral. I replaced it by a Riemann sum of N = 8 panels written out as
   8 `pow(10, ...)` terms per load. The integrand is increasing in t (T0 < T_ch always), so the left sum is a lower
   bound and the right sum an upper bound of the true integral. Error is large: at the worst corner for L4/PK5/124/25 min,
   left8 = 15.11, true = 16.91, right8 = 18.72 (my python). Safe only in the direction chosen. Monotonicity is argued
   by me, NOT checked by the stand (the stand judges the sum, not the claim that the sum bounds the integral).
2. **Real t_h -> grid.** t_h = n x 0.5 min, n = 2..60 (1 to 30 min). "Any real number" is not available as a choice
   (continuous slots need affine quantities). The range 30 min is my cap; R4 alone forces t_h <= 24.6 min, so no loss.
3. **Make REFUTED sound for the real problem.** Mode B ("c11.json"): LR is evaluated with the RIGHT sum at the upper
   end of the grid cell (n+1)*0.5 min, while damage, weekly time and cost use the lower end n*0.5 min. Every real
   t_h in a cell is covered by this optimistic design. So REFUTED(B) => no real program exists. Mode A (left sum, same
   t_h everywhere) is the converse: EARNED(A) => a real program exists. Both claims rest on my monotonicity argument
   (LR and the integrand rise with t_h; Dm, Wk, cost rise with t_h) - checked only by me, with mpmath (see below).
   Safety margin of B at N = 8: smallest gap to feasibility is 1.0 min (T_set 126: R4 cap 20.6 vs needed 21.6),
   larger than the 0.5 min cell; the other set-points fail by 2 to 12 min. With N = 4 B is too loose: a variant
   (work_c11/probe7b.json, 2 set-points) came out EARNED, which is false for the real problem. So the verdict depends
   on N; N = 8 was chosen after checking, not by the stand.
4. **R2 and R3 per load** are kept in c11.json. In the 7-requirement variants (work_c11/gen7.py) I merged them by
   hand (one Dm limit = min of the four budgets, valid because Dm is the same for all loads; Pm = min over loads
   of Tmax minus T_set - 1.5): equivalent, merged by me. Used only to try to get minimal_conflicts.
5. Heat-up ignored, "Celsius as difference": as in the problem statement / format. Cost "per minute of cycle time"
   read as all cycle minutes of the week (50 cycles).

## COULD NOT EXPRESS
- An **integral** (needs a quadrature rewritten by hand; accuracy N-dependent; the stand cannot check the bound).
- A **continuous choice** t_h entering nonlinearly (grid only), and so "the minimal real t_h" - the stand cannot return it.
- **Which requirements conflict**, for this size: `minimal_conflicts` is skipped for > 8 requirements ("13 requirements:
  subsets over 8 not enumerated"); with 7 requirements the run was killed at 900 s (31860 designs; and also on a
  3240-design cut, 2 set-points x n 36..50, N = 8). So the conflict set is not available from the stand; I derived it by hand (below).
- A one-sided (bounding) statement: "this sum is a lower/upper bound of that integral" - the format only has equalities.

## DOC GAPS
- BRICKS.md does not say that `minimal_conflicts` is skipped above 8 requirements AND becomes infeasibly slow
  (> 15 min) already at ~3000 designs with 7 requirements and 8 function terms per load; for design spaces of tens of
  thousands it is unusable.
- `min`/`max` work in laws but not in requirement bounds; bounds list does not say functions are excluded.
- A requirement's bound unit: the bound is read "in the quantity's own unit" but a given used as the bound must itself
  carry that unit (budget given in "" vs quantity in min is a BRICK ERROR) - not stated.
- Nothing is said about how to write an integral or a conservative quadrature; no way to state that a law is only a bound.
- Run time of tens of thousands of designs (6-9 min at 12 ms/design) is not given; no hint to prune with `where`
  (I did not use `where` because the problem's own R3 is meant to be a judged requirement).
- "closest_design" definition is not documented.
