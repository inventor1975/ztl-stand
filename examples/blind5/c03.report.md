# c03 report: Solar thermal hot water, annual back-up energy (problem 3)

Final verdict: **EARNED** (optimal: true, but only inside a run-time price window, see APPROXIMATED 1).
Design: collector F2, n = 5, tank 750 L, no insulation upgrade, price 4.6232 kEUR.
Stand: R1 worst Eyear = 3642.68 kWh (limit 3700); R2 worst summer T = 72.89 C (limit 80). R3: V/A = 750/11.5 = 65.2.

## EXPRESSED FAITHFULLY
- Catalog: 6 collectors (A, eta0, a1, a2, price as listed), n = 1..16 (`integers`), 5 tank volumes, insulation none/upgrade (factor 1 / 0.6, price 0 / 0.25).
- Four seasons as `modes`; per mode H, Ta, Tc are independent ranges, hs fixed. The shared draw D (540..660 L/day) is a given NOT overridden in any mode, so the manual says it is one value in all modes (with `totals`). The same Ta is used for the collector and for Tr = Ta + 8 (one define).
- The tank temperature T is an implicit root per season (`search` [0, 150]) of the heat balance, written with the real max(0, ...) efficiency as `if(...)`. The 0.024 factor is not typed: it is carried by the units (UA in W/K, load in kWh/day, all converted to SI power).
- G = 1000 H/h written as `H*dd/hs` (H in kWh/m^2/day, hs in h, dd = 1 day): unit-checked, no hand factor.
- Back-up: Bk = cw*D*if(T > 45, 0, 45 - T) per season; annual = `totals` Eyear = sum over seasons of days*Bk with weights 90/92/92/91 days.
- R1 (Eyear <= 3700, worst case over the whole box), R2 (T <= 80 in every season, as a per-mode requirement), and R3 (50 <= V/A <= 100) as `where` on exact values. Minimum price objective n*price + tank + upgrade.
- Units: "checked: every law's dimensions agree".

## APPROXIMATED
1. **Run-time price window (not safe by itself, checked partly by the stand).** The full brick (220 designs after R3) cannot finish in 900 s: designs near feasibility cost about 105-120 s each (see TOOL OUTPUT). The delivered c03.json adds `Pmin = 4.5 kEUR` in `where` (design price >= 4.5). That is my cut, not part of the problem. Designs cheaper than 4.5 were handled so: 27 refuted by the stand in the full-brick run (out1), 5 more refuted by the stand in a window run from 4.2 (out2), and 16 designs (roughly 3.3..4.2 kEUR) only by my own python (worst-corner computation, same numbers as the stand where compared). So "optimal: true" in c03.json is only for price >= 4.5; for the whole catalog the optimality rests on the stand for 32 of 48 cheaper designs and on me for 16. Direction of risk: if my python were wrong for one of those 16, a cheaper design might exist.
2. **Tank price and UA are irrational** (0.9 (V/300)^0.8, 1.8 (V/300)^0.6); `computed` has no pow. I put them as decimal catalog values rounded to 6 digits (price) and 8 digits (UA), exact fractions, with no tolerance. Relative error of UA < 1e-8. Not conservative in a strict sense (neither up nor down); effect on the margin (3642.7 vs 3700, 72.9 vs 80) is negligible but nobody checks it except me.
3. **Laws with T cannot go through `define`** (BRICK ERROR "'T' is not a quantity" under totals), so eta(T) is typed inline twice in the heat-balance law (the `if` condition and the value). Same math, longer text; the stand checks the law as typed.
4. R3 is a `where` filter, not a checked requirement: exact values, no uncertainty, so it is equivalent. The stand does not "judge" it, it only excludes designs.
5. Bounds Tmax, Emax, Rmin, Rmax are declared as given quantities with units (as the manual asks); the hot-water set point 45 C, the offsets 6 C and 8 C, cw are givens. No conversion is typed in a law.

## COULD NOT EXPRESS
- Nothing in the physics was impossible to say, but: the format has no `pow` in `computed`, so the tank price/UA formulas must be pre-evaluated by hand (item 2 above).
- A define cannot contain a derived quantity (T) in a `totals` brick: no named `dT`, `eta`; they must be inlined.
- No way to say "search the cheap designs fast": there is no per-design time cap or ordering hint, so the 900 s limit forced the manual price window.
- Whether D is shared is expressed only implicitly (a given that no mode overrides). It works as described, but there is no explicit "shared" flag, and I did not run a variant to prove it (see DOC GAPS).

Both match (here the stand's witness is the worst corner, not the nominal point; for the cheapest design F1/2/300 it was the nominal point, 1533.27, while the worst corner is 3174.7 over).
- First feasible in my list: F2/5/750/none 4.6232, then T2/3/500/none 4.8043 and F1/7/750/none 4.8132. So the stand's design is the cheapest by my python as well, over all 220.

## DOC GAPS
- `totals` + implicit law + `define`: BRICKS.md does not say a define cannot hold a derived quantity under totals (copy renaming breaks it). The error message is clear enough but the guide should say it.
- No example of `totals` in examples/; I wrote it from the text alone. It worked, including an implicit `search` quantity per mode.
- No statement of what a design costs in time: with 13 toleranced dimensions and an implicit law the stand needed 2 min per design, so a catalog of a few hundred designs is out of reach under the 900 s limit. The doc only mentions "20 s per design for nine toleranced quantities".
- `by` in REFUTED is at the stand's witness (nominal for some designs, worst corner for others); easy to misread as worst-case overshoot.
- Unit for an hour-of-sun irradiance: G = H/hs needs the day unit explicit (`H*dd/hs`); not obvious from the doc, I got a units error first.
