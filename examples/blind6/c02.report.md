## EXPRESSED FAITHFULLY
- Both catalogs as listed (6 cables, 7 breakers; the S column is a field too), four independent slots, 1764 designs.
- V0 395..415 V, ks 0.060..0.085 V/A as ONE given each (used in all places in a situation), V_bus = V0 - ks (Ia + Ib).
- theta = T_amb + 60 (I_run/Iz30)^2 with T_amb = 38, R'(theta) = R20 (1 + 0.00393 (theta - 20)), X' = 0.08, dV = sqrt(3) I L (R' cos + X' sin) with sin = sqrt(1 - cos^2) (cos 0.85 running, 0.40 starting), Iz(38) = Iz30 sqrt((90-38)/60) (90, 30, 60 are separate givens in C), terminal = V_bus - dV. All written as the problem's formulas, with units (V, A, mohm/m, m, EUR/m, EUR).
- Three situations as `modes`, each with its own currents (independent ranges), each with its own requirements: R1 (both terminals >= 380 in S1), R2 (starting motor >= 340 in S2/S3), R3 (V_bus >= 352 in S2/S3). Currents: S1 50..56 and 30..35; S2 M1 = 53 x k (k 5.8..6.4), M2 30..35; S3 M1 50..56, M2 = 32 x k.
- R4, R5, R6 per feeder, as requirements judged by the stand (not pre-filtered by `where`).
- Objective: C1.price*L1 + C2.price*L2 + B1.price + B2.price.

## APPROXIMATED
1. "Highest running / starting current" has no operator. I used the range itself: theta and R4 read a given `Irun1` in 50..56 (not the 56), R5 reads `kls1` 5.8..6.4 times 53. "Holds for every value in the range" equals "holds at the highest" because every margin is monotone. Safe; the stand checks it (m4/m5 are guaranteed ranges, I did not type 56 or 339.2).
2. Starting current needs a product of two uncertain things (53 x k_ls): each mode overrides a base current `Ib` and a multiplier `k` (S2: Ib1 = 53 exact, k1 5.8..6.4; running: k = 1). Exact, no hand algebra, but 6 extra givens overridden per mode.
3. The theta/R4/R5 currents (`Irun`, `kls`) are separate quantities from the situation currents (`Ib*k`). The problem says "all ranges independent", so this is as stated; worst cases coincide anyway.
4. Margins `m4 = In - 1.1 Irun`, `m5 = 8 In - 1.25 kls Iref`, `m6 = Iz - In` are derived quantities required >= 0 (a requirement cannot take a derived bound). Algebra-only rewriting; the stand judges them.
5. R2 is applied literally: only the STARTING motor >= 340. The running motor's terminal in S2/S3 is not required (the text "at least 380 while running" is listed as R1 in S1 only). Reading it as also required in S2/S3 would be impossible anyway (V_bus min in S2 is 363 < 380), so I do not think a different reading was meant. My judgement, not the stand's.
6. T_amb = 38 only (as the problem says); the 5..38 range is not used.
7. Limit question: the first `find` over 0..400 m (precision 0.1) was killed by the 900 s limit (see TOOL OUTPUT; its partial bracket 250 EARNED / 275 REFUTED was already printed by the stand). I then narrowed the search window to 250..254 with precision 0.5 using that bracket, so the answer is a bracket of 0.5 m, not a number. The window choice is mine; every try inside it is the stand's. `find` is in a copy (`c02_find2.json`, also `"conflicts": false`), not in c02.json, so c02.json answers the design question at L1 = 160.
8. Component version only: three transformer instances (one per situation, V0 and ks drawn independently per instance, harmless because each requirement lives in one situation); which feeder starts in which situation is written by hand into two files (`feeder1.json` starts in S2, `feeder2.json` in S3); `assume` ranges are my wide choices (currents 0..400, V_bus 300..420, L 0..600), contracts `"bands": "arriving"`. The ranges of the system equal the flat brick's (see below), so nothing was lost there; EARNED is sound by construction.

## COULD NOT EXPRESS
- A maximum of a range ("the highest running current") as an operation: only by "for all values", see APPROXIMATED 1.
- "ks = ONE shared value" across all three situations: without `totals` each mode is judged on its own and may take its own ks and V0. Harmless here (no requirement spans two situations), but a requirement that did could not say "same ks in S2 and S3".
- "Largest L1 for which ANY design exists" is a `find` over a catalog; no way to say it without re-judging all 1764 designs at every try (each failing try = all designs refuted, 2-4 minutes). That is a cost, not a missing word.
- A component's cost that depends on a system quantity (cable price x system length): the component's own `cost` is computed at the component's own placeholder length and the stand does not complain (see DOC GAPS 1). Worked around with `F1.C.price*L1 + F1.B.price + ...` in the system's objective.

## DOC GAPS
1. Section 7d "Tuning a component's parameters": the component's `cost` is the component's objective read at its own given values. If it depends on an input (cable price x L), it is computed at the brick's placeholder input value, silently. The sentence about `COMPONENT.slot.field` is the way out, but nothing says to use it for this. A warning or a refusal would be right (I got a plausible-looking wrong 2068).
2. Section 8/9: with `modes` the output has no `units` line, so step 1 of "Before trusting a new JSON" cannot be done; I cannot tell whether units were checked.
3. `find` over a catalog: nothing says that every failing try judges all designs (minutes here), nor that a killed run still prints the bracket (`stopped`, `stopped_at`, `proved`) - this is useful and should be written.
4. 7d does not say that a component with `"inputs": {}` is allowed (it is), nor that the bands string `"arriving"` may be set per input (it worked).
5. Section 7b: "a given that no mode overrides ... may take different values in different modes" (without totals) is in brackets at the end of another point; a reader needing a ONE shared value across modes (ks) does not find an answer there.
