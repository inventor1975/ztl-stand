# c05 report: Which embroidery machine to buy (problem 05)

Two bricks: `c05a.json` answers (a), `c05b.json` answers (b). The required name `c05.json` was not written; I ran both files under their own names.

## EXPRESSED FAITHFULLY
- (a) `c05a.json`: one slot M with two listed items (Regular, Heavy-duty). Each item has CF0 as an exact value, and CF1..CF6 each as a value with tolerance 0.03, so each is its own independent 97-103% box. r is a given range [0.09, 0.11], one quantity shared by both machines. Law: `NPV == CF0 + sum CF_k * d_k`, with `d_k = 1/((1+r)*...*(1+r))` written as k explicit factors through `define`. Requirement NPV >= 1165, with `report: all` so both machines are judged. No objective.
- (b) `c05b.json`: exact listed flows, no tolerances, two laws NR and NH, `Diff == NH - NR`. Requirement Diff >= 0, with `find largest r` from 0 to 0.3, precision 0.00001.

## APPROXIMATED
- (b) is not asked as a root-finder. I used `find largest r` such that heavy >= regular on all of [0, r], which only equals the crossover because Diff(r) is positive below the crossover and negative above it. The check below confirms this (one sign change). The stand does not check it. I assumed it, and my own script confirmed it.
- The answer is on a 1e-5 grid (a quarter of a hundredth of a percent), enough for two decimals. Nothing else is approximated.

## COULD NOT EXPRESS
- Nothing in (a).
- For (b), "the rate at which two NPVs are equal" has no native form (no root-finding of a derived quantity). I used the `find` workaround above. I added a given `usd = 1 USD` so the unit check passes (a bare dollar amount against a dimensionless discount factor is a BRICK ERROR, which I hit once).

## DOC GAPS
- BRICKS.md gives no recipe for "the rate where two quantities are equal" (a root, as against a limit). I had to infer from the `find` section that "largest r with Diff >= 0 on [0, r]" works, and that it only works if the sign changes once.
- It does not say that listed items with `tolerance` per field are fine for a repeating cash-flow row (it is, but the format shows only simple examples), nor that a `define` of a power of (1+r) is accepted. It was.
- It does not say that `how: outer range` for a sum with a shared r is tight here. It is tight at this lower end only by luck of monotonicity (r only at its endpoint), and the doc's wording "may be wider" is correct.
- For REFUTED designs with `report: all` the output gives only the witness overshoot, not the worst case, so (a) needs a second route (`each_requirement` or a guaranteed-range run) if the worst-case NPV of a failing machine is wanted. I did not try that.
