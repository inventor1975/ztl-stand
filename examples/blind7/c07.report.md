Bricks: c07a.json (feasibility: both requirements) and c07b.json (best worst-case E within the power limit). The command in the task names c07.json; I ran c07a.json and c07b.json with the same command line. There is no c07.json.

## EXPRESSED FAITHFULLY
- Luminaire type: slot LUM, four one-item catalogs F3, F2, L1, L2. Each carries Phi, W and the three CU values (RCR 6, 7, 8), exactly as in the table.
- N = 1..5: an integers catalog, slot NL.
- A = 120 ft^2 (exact). LLF in [0.75, 0.85] and RCR in [6.5, 7.2] are independent ranges.
- CU: law `CU == table(RCR, 6, cu6, 7, cu7, 8, cu8)`, linear interpolation between the tabulated RCR values.
- E: law `E == N*Phi*CU*LLF/A`. Ptot: law `Ptot == N*W`.
- Pmax = 120 W as a given, with the source "1.0 W/ft2 x 120 ft2". It is written as the power limit that the problem itself states (total installed power at most 120 W).
- c07a requirements: E >= 50 (fc) and Ptot <= Pmax.
- c07b: requirement Ptot <= Pmax. Objective `minimize -E`, `case: worst`. This maximises the worst-case E.
- Both bricks use `report: all`.

## APPROXIMATED
- Lumens are dimensionless (unit ""), because `lm` is not a unit in the stand. E therefore has unit 1/ft^2, which is footcandles (lm/ft^2). Safe: the unit check passes, and it is only a label.
- "Highest worst-case E" is done as minimising -E in the worst case. The stand's objective case is a proved upper bound of the worst case, and it named the winner optimal. Not hand-computed.
- The LPD limit is written directly as 120 W. The problem gives both forms and says they are equal.

## DOC GAPS
- There is no photometric unit (lm, fc). The workaround (dimensionless lumens, 1/ft^2) works but is not mentioned; a note would help.
- BRICKS.md does not say how "maximise" is written. I deduced `minimize -E` with `case: worst` from section 7. The negation also reverses what "worst" means, which I reasoned out (worst of -E is -(min E)). The result matched, but a sentence on this would help.
- The reported objective value for c07b is in 1/ft^2 (45.26 fc) while the judge_log shows E in 1/m^2 (about 487). It says "unit_from: the unit of the prices", which is odd for a non-price objective, but it is consistent.
- `closest_design` in c07a is a "smallest overshoot found" and mixes units of different requirements, as the doc says. It is correct but easy to misread as "the best design".
- Using `table` with a dimensionless RCR needs no unit division. The doc covers this.
